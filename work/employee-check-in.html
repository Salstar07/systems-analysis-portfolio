01 / BUSINESS PROBLEM

A check-in needs
a dependable hand-off.

The application supports an employee check-in process at CivilSE. Its business purpose connects a user submission with a recorded entry and communication to the intended Teams audience.

A useful user experience must make the state of a check-in understandable: submitting a form, running an automation and delivering a notification are separate stages. Detailed submission fields, users and acceptance criteria still need to be supported by the approved requirements.

02 / MY CONTRIBUTION

Application development.
Integration investigation.

I developed the Employee Check-In Canvas application and investigated integration issues involving Power Automate, SharePoint and Microsoft Teams.

Verified Basis: owner confirmation. Saalima confirms this development and investigation work, and reports successful SharePoint logging and Teams notifications after connection-reference corrections. Original execution records have not been supplied for this portfolio.

03 / REQUIREMENTS

Define success
at each stage.

The following criteria explain the workflow and provide a basis for reviewing its requirements. They are not a substitute for the original specification.

  • User experience: the user needs to understand required input, submission feedback and what to do if processing fails. The implemented fields and screen behaviour need confirmation.
  • Recorded check-in: validate that the intended SharePoint entry exists and contains the expected submitted information.
  • Workflow and communication: distinguish automation execution from delivery to the intended Teams destination. A successful form interaction alone does not establish both.

Follow the check-in
through the workflow.

The confirmed technology context is Power Apps Canvas, SharePoint, Power Automate and Microsoft Teams. The diagram summarises their relationship without disclosing internal lists, flow definitions or connection details.

Investigate the
connection boundary.

My work combined Canvas app development with investigation of integration issues. Connection-reference corrections were followed by reported successful SharePoint logging and Teams notification tests.

06 / TESTING

Submission, execution
and delivery.

  • Submission: did the app accept the intended check-in? This tests the user interaction and submission handling.
  • Workflow execution: did the relevant automation run and complete its expected actions? Review the run record and each relevant result.
  • Notification delivery: did the expected Teams message arrive in its intended destination? Verify delivery independently of the app’s feedback.

Verified Owner-confirmed result: SharePoint logging and Teams notifications succeeded after connection-reference corrections. The complete test matrix, timestamps, failure-path results and original run evidence remain to be supplied.

08 / OUTCOMES

A bounded integration
result.

The owner-confirmed result is successful SharePoint logging and Teams notification delivery in the reported tests after connection-reference corrections. It demonstrates progress on the tested integration path; no time-saving or organisation-wide impact metric is claimed.

09 / LIMITATIONS

Keep the test boundary
visible.

Immediate offline transmission, complete location/weather functionality, all navigation changes and production-wide reliability are not verified here. A successful integration test does not establish every feature, network condition or user journey.

The next step is to link an approved requirements and test record to the reported results, then confirm the application’s current deployment and acceptance status.
